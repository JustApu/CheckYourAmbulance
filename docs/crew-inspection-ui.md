# Crew inspection screens

[issue #85](https://github.com/JustApu/CheckYourAmbulance-archive/issues/85). Non-normative implementation notes. The product rules are SPEC §6.1–§6.5, §7.3 (REC-1–REC-4), §7.4 (CON-2, CON-3, CON-6), §16.4 and §17.3, and the shell conventions in [application shell](application-shell.md). Code: `cya/inspections/views.py`, `api.py` and `templates/inspections/`; the row fields come from `cya/attention/` ([attention views](attention-views.md)).

## Pages

| Route | What it shows |
|---|---|
| `/inspection/` | Active vehicles with their operational status. Every built-in role (SPEC §3.3); the server enforces it like the other sections. |
| `/inspection/vehicles/{id}/` | A responsive vehicle-name/status heading, inspection-history and deficiency tasks, and one entry per vehicle checklist (SPEC 6.0.0 SES-7): Continue or Join its one session in progress, otherwise Start it, or Resume the signed-in user's newest incomplete session of it with Start a new inspection secondary. Active sessions and the signed-in user's own ended sessions remain visible. |
| `/inspection/vehicles/{id}/print/` | The paper checklist for outages (issue #9 Part A): the vehicle's current checklist with blank result, count or value, initials and time columns, and one seal-or-contents row per kit, for printing on US Letter. Linked from the vehicle page as "Paper checklist for outages". Same access as the vehicle page. |
| `/inspection/kit-reference/` | The kit reference: what a complete kit contains, per kit type, from each active checklist template's revision in force. Printed once per revision and laminated. Same access as the vehicle page. |
| `/inspection/sessions/{id}/` | The checklist screen. A participant only: a session the user did not join answers 404 exactly like one that does not exist. |

A vehicle in another organization, an inactive vehicle and a malformed id are all 404. A signed-out visitor is sent to sign-in and a user with no role gets 403, as for the other sections.

## Paper checklists for outages

The app is online-only, so an outage stops inspections in the app. Crews then use printed checklists kept in each rig (SPEC §17.8 DEP-11; owner decisions recorded on [issue #9](https://github.com/JustApu/CheckYourAmbulance/issues/9)).

- **The outage sheet.** `/inspection/vehicles/{id}/print/` lists the checklist in force for the vehicle when it is printed, grouped by compartment and vehicle system in the checklist screen's order. Each row has tick boxes for the item's allowed outcomes (Pass, Fail, Unable, N/A), a blank for a count or value where the item records one (with the expected quantity for quantity items), and blanks for initials and time. The header names the vehicle, each checklist template and revision, the version IDs and the instant the sheet reflects (in station time; issue #235), plus blanks for the date and shift.
- **Kits on the outage sheet.** Each kit instance is one row, not its contents. A kit designated sealed (SPEC §10.1 SEAL-1) offers "Seal intact", with the crew ID and earliest expiration written on the seal, or "No seal or broken: contents checked" against the kit reference; any other kit offers only "Contents checked against the kit reference". Both note exceptions. Kits do not start new pages.
- **The kit reference.** `/inspection/kit-reference/` lists what a complete kit contains (items and expected quantities) once per kit type, from each active template's revision in force, in three columns on US Letter. Print it once per checklist revision and laminate it; reprint when a revision changes. Each block names its template, revision and version ID so a laminated copy can be matched to the revision on the outage sheet. It is the agency standard: vehicle overrides are not applied. Until reusable kit definitions exist ([issue #129](https://github.com/JustApu/CheckYourAmbulance/issues/129)), a kit type is named by the label of the kit its checklist definition names, and the reference cannot yet mark items with expiration dates.
- **Paper size and pages.** Both print on US Letter. A long checklist continues on further pages rather than shrinking the type. Every printed page of the outage sheet repeats the vehicle, checklist revision and version ID in its table header, so loose pages can be matched up. Every page of the kit reference names its revisions and version IDs in a running header in the top margin. That running header and the page numbers ("Page N of M") come from the browser's print margin; Chromium-based browsers print them, other browsers may not.
- **No personal data.** Both pages are standalone, without the app header, so neither the page nor the printout carries the signed-in user's name. They show checklist definitions only: no check results, deficiencies or crew names.
- **Not a live record.** Printing records nothing in the app. If the checklist changes after printing, print new copies; the version ID identifies the checklist a sheet was printed from.
- **Failure.** If the checklist cannot be resolved, either page answers 503 and prints nothing rather than a partial document.
- **Sealable cabinets.** A compartment designated sealable (SPEC §10.2 CAB-1, CAB-9) prints one "Sealed cabinet" row (seal intact with crew ID and earliest expiration, or all contents checked) instead of its items, even when it holds only kits. Kits inside it are marked as covered by the cabinet seal while it is intact. Designations are read as of the sheet's instant; see [kit obligations](kit-obligations.md#sealable-designations) for how they are set.

**Outage procedure for the rig.**

1. Keep blank outage sheets for each vehicle, and the laminated kit reference, in the place your agency designates; the location varies by agency.
2. During an outage, record each check on the sheet: tick the outcome, write any count or value, and add your initials and the time. For each kit, confirm the seal or check the contents against the kit reference.
3. Keep completed sheets after the outage. Paper results are entered into the app once the downtime has ended, and the sheet can then be shredded. No separate review of the paper records is required.
4. Until the back-entry feature exists (issue #9 Part B, which needs its own SPEC amendment first), paper results are not entered as ordinary live checks (DEP-11). Keep the completed sheets until back-entry is available.
5. Reprint blank sheets, and the kit reference, whenever a checklist revision changes.

## Supervisor fleet readiness

`/fleet/readiness/` shows compact summaries of each active vehicle's explicit operational status, inspection progress and separate Failed, Overdue, Missed, shown high severity deficiency and suspension counts. The high severity summary uses the top two active, organization-configured severity ranks at the picture's as-of instant and displays their configured labels; each deficiency is ranked by the in-force revision of its level code at that instant (including retired levels), with its recorded revision's rank as fallback. If no levels are active, it counts all shown active deficiencies. The optional attention filter includes vehicles with non-In-Service status, failed/overdue/missed checks, active deficiencies at either of the top two configured severity ranks, suspensions, or a truncated deficiency list. These signals do not combine into a compliance or operational status. The on-screen help says this in plain words and names the levels it counts ("an open Critical / High problem", or "any open problem" when no level is active; issue #235). The live line says the page updates every 20 seconds (issue #278; it was 60) and, when instant updates are connected, that changes on the first few vehicles (at most three sockets per page) show within 10 seconds plus the time to refresh the panel (SPEC 8.1.0 §17.3). Each card expands to the existing obligations, deficiency and suspension details, including their truncation notices. Inspection, deficiency and status links open the current workflows; the deficiency summary link opens the oldest active deficiency, an `as_of` page remains a static historical picture, and the status link is explicitly labelled current. The live panel re-reads from the server and retains which vehicle detail sections were expanded.

`tools/browser_smoke.mjs` checks the readiness card layout, independent count labels, workflow links, attention filtering, keyboard disclosure, 48 px targets and horizontal overflow at 375, 600, 768, 1024 and 1440 CSS pixels and at a narrower 200% zoom approximation.

The landing page uses the configured checklist-template labels and lists each checklist bound to the vehicle ([issue #256](https://github.com/JustApu/CheckYourAmbulance/issues/256) Part D). Each vehicle checklist has at most one session in progress (SES-7), so a checklist in progress offers Continue to a participant and Join to anyone else, never Start; a different checklist on the same vehicle can be started at the same time. A checklist no longer bound is still listed while it has a session in progress. There is no separate start. When a checklist has no session in progress but the participant has an incomplete one, Resume is primary and Start a new inspection is secondary; while another session of that checklist is in progress, the page says the incomplete one cannot be resumed and offers Join instead (SES-3). A nonparticipant's open row in the list points to its checklist's Join button. A start can still join a session opened concurrently after page load; the command remains authoritative.

`tools/vehicle_landing_smoke.mjs` exercises the real vehicle-page script and CSS with synthetic sessions on two checklists at 375, 600, 768, 1024 and 1440 CSS pixels. It checks the start/join/continue distinction per checklist, that no separate start is offered, Resume and its refusal while another session is in progress, accessible task names, 48 px targets and horizontal overflow. `npm run test:browser-smoke` runs this alongside the checklist and shell smoke.

## Session endpoints

Authenticated same-origin JSON (CSRF protection stays on). The command layer authorizes, audits and replays by operation id; these views parse and map outcomes. Operation ids must be UUID v4. A refusal never echoes the command's text.

| Endpoint | Body | Result |
|---|---|---|
| `POST /api/v1/inspection-sessions` | `operation_id`, `vehicle_id`, `template_id`, optional `separate` (boolean; `true` is refused while that checklist has a session in progress) | `SESSION_OPENED`, `SESSION_JOINED` (the checklist's session in progress, SES-7) or `ALREADY_PARTICIPANT`, with `session_id`, `state`, `checklist_version_id` and `resume_deadline_at` (SES-8) |
| `POST /api/v1/inspection-sessions/{id}/reopen` | `operation_id` | `SESSION_REOPENED` with `resume_deadline_at` (a participant only, before the session's resume deadline and while no other session of the checklist is in progress, SPEC SES-3, SES-7, SES-8) |
| `POST /api/v1/inspection-sessions/{id}/end` | `operation_id`, optional `state` `CLOSED` or `INCOMPLETE` | `SESSION_ENDED` (a participant only) |

Rejections use the common shape: 400 `MALFORMED_REQUEST` (bad or unknown fields, a non-v4 id), 401, 403 `FORBIDDEN` (including a nonparticipant and an unknown session), 409 `SESSION_IN_PROGRESS` (a separate start, or a reopen, while another session of that vehicle checklist is in progress), 409 `SESSION_DEADLINE_PASSED` (a reopen at or after the session's resume deadline, SES-8, [issue #256](https://github.com/JustApu/CheckYourAmbulance/issues/256) Part E; a check into such a session gets the same code from the checks endpoint), 409 `SESSION_UNAVAILABLE` (the command refused otherwise: no such active template or vehicle, already open, not open) and the usual 503 codes.

The session screen reads its rows with `GET /api/v1/vehicles/{id}/checklist?session_id={session}`: the rows of the version the session pins (CHK-4), with the vehicle's current state on each. Only a participant of a session on that vehicle gets them; any other session id is 404 `NOT_FOUND`, a malformed one 400 `MALFORMED_REQUEST`, and `session_id` with `checklist_version_id` 400 `MALFORMED_REQUEST` before the session is looked up.

## Checklist screen behavior

- **One tap, no Save button (REC-1).** Pass on a presence/condition or special-observation item sends the check at once. A quantity item takes a count (the server derives Passed or Failed from the target); a measurement item takes a value in the item's unit and sends Passed. A vehicle-reading item points to the odometer form (the server refuses it as a check).
- **Pending, Saved, Failed, Unconfirmed (REC-2, REC-4).** Pending is shown while the request is out. Saved applies only to a `COMMITTED` answer from the server; it is announced to screen readers once, by the shell's toast (the item list is not a live region, so a re-render after a save is not read out; issue #235 B1), but not shown as a line, because the outcome button then shows the recorded result (issue #140). A definite server refusal is Failed with a plain-words reason. Anything else (the request failed, timed out, or the answer was not a definite one) is Unconfirmed: the write may or may not have committed. Retry resends the same request with the same operation id; a new tap is a new decision with a new id. The shell's indicator gained the `unconfirmed` state for this.
- **Scroll and keyboard focus after a check.** Rebuilding the checklist keeps the visible item at its viewport position. Focus moves to the item row while its action is disabled during a save, then returns to the action when the save result is rendered. The deficiency dialog keeps focus while it is open and restores it to the item when closed. If the item changed or disappeared, focus moves to the item or checklist list. Acknowledgement announcements continue through the existing status indicators.
- **Conflict dialog (CON-2, CON-3).** Each check carries `basis_check_id`, the newest effective check shown for that item (and kit instance). If the server answers `CHECK_CONFLICT`, the dialog names who recorded what and when and says nothing was saved from the tap. Cancel drops it. "Record mine too" sends a new operation id with `acknowledges_check_id`; if yet another check landed, the dialog appears again. The dialog keeps its row, so the proceed still goes out when a live reload has dropped the row from a Needs attention only list (for example because the other person's Pass satisfied the obligation); the basis and the acknowledgement are both fixed to the check the warning named, whether or not the row is still listed, so a newer check that a live reload has shown while the dialog was open cannot be skipped: the server answers with a conflict and the dialog appears again for that check. The outcome is said in the status line because the row is no longer there to show it. Whether to show that someone is viewing an item stays out (CON-6).
- **Live updates (SPEC §17.3).** The screen opens the vehicle socket, naming its session so a participant also gets the rows a check changed (SPEC 8.3.0; see [live updates](live-updates.md)): those are shown without a read when they are newer than the rows shown. Otherwise a push is only a hint: it triggers a reload of the checklist, and so does every (re)connect and the tab becoming visible, so a missed message cannot leave a wrong list. Any reload that starts after a push arrives covers it, so the saver's screen skips the push for its own committed check (it already reloads after the save's answer) and holds a push that arrives while one of its saves is unanswered until that save's reload. A refused or unanswered save, or an answer slower than 2 seconds, leaves the push its own reload, within §17.3's 2-second allowance ([issue #278](https://github.com/JustApu/CheckYourAmbulance/issues/278)). When the socket drops, a prominent banner says the screen may be out of date and the screen reconnects with backoff (1 s up to 30 s). The banner does not claim that unsaved items were not recorded: an item shown Unconfirmed may have committed, so it says to use that item's Retry (same operation id) and not a new tap. If the server closes the socket because the sign-in ended or access changed (close codes 4401 and 4403) the screen stops reconnecting and the banner says so and asks the person to sign in again. If a reload fails, a second banner says the list may be stale. The shell's own banner still covers the browser going offline.
- **Views and filter (VW-1, VW-2).** Normal and Priority and Needs attention only change the list at once and are saved through the audited preference endpoint, so they follow the crew member to other devices. A failed save only means the choice is not remembered; it never blocks the list.
- **Compartment navigation (issue #103).** A new inspection session starts at the compartment overview. An EMT can open a vehicle area/compartment, see its checklist items grouped by physical kit instance, and return to the overview at any time; All items keeps the flat list and existing filters. Each area card gives a short line with the counts that need action ("12 of 150 checked · 3 due · 1 overdue · 10 open problems"), and a **Details** disclosure beside it lists the rest (due soon, not due, not required, exceptions; owner decision, issue #235 C2). An open Details stays open, and focus stays on it, through live re-renders. In split view the cards show only how many items are still due. When nothing is due, the checklist bar says "Nothing is due right now." and shows no progress bar, so a full bar never stands for unchecked work. The selected view and visible item are stored in browser local storage under a key containing both the authenticated user ID and inspection session ID; malformed/stale keys fall back to the overview, and another user or a new session cannot reuse them. Resuming a saved position also restores focus (issue #235 B2): to the saved item, or to the open area's heading when no item was saved, unless the person has already moved focus, so Tab continues from there rather than from the skip link. This navigation position is per browser/device; unlike the audited checklist view/filter preference, it is not synchronized to the user across devices.
- **Split view (issue #194).** In Compartments, on screens 64rem (1024 px) and wider (tablets in landscape, laptops and desktops), opening an area keeps the area list in a narrow column beside that area's items.
  - Each card there shows a short count ("2 still due" or "Nothing due"), and the open area is marked (`aria-current`).
  - Choosing another card switches areas without going back to the overview.
  - A focused card stays focused through live updates.
  - The view follows the screen width as it changes (rotation, window resize). Narrower screens keep opening one area at a time.
- **Long-checklist aids (issue #194).** An open session (not verification, not ended) has a bar at the bottom of the checklist. It stays on screen while the checklist scrolls, and on phones it sits directly above the tab bar.
  - **Progress** counts the whole checklist for the current window, using the server's area counts: "N of M checked · K still due", where M is checked plus due, due soon and overdue. Not-due, no-obligation and exception rows are left out. Needs attention only does not change the counts.
  - **Next unchecked item** moves to the next due, due-soon or overdue row on this screen after the last item that had focus (or the first item on screen), opening its area in compartment view. It wraps to the start, scrolls the item clear of the bar, focuses it and outlines it until a check is recorded on it. If nothing is left, it says so; if Needs attention only hides due rows, it says to turn the filter off.
  - **Sections** opens a list of areas, each with what is still due. Choosing one opens that area in compartment view, or moves to its first item in All items. Escape closes the list and returns focus to Sections.
  - The bar only moves and reports. It records nothing, and it is hidden when printing.
- **Known deficiencies and status (VW-3).** Unresolved deficiencies show beside their item; the operational status and any restrictions are at the top.
- **Separate check result, window state, and deficiency lifecycle (issue #104; SPEC §7.5, §8).** The checklist labels the current inspection window separately from the latest recorded check, shows a concise state on the item and a deficiency's current lifecycle status and severity independently, and keeps Pass, Fail, Unable to inspect and measurement controls as actions. In compartment view, the compartment and kit instance headings provide location and kit context once; flat and verification views include those details on each row. When a deficiency block already explains the attention state, the repeated Needs attention badge is omitted; the badge remains for attention without a listed deficiency. A Pass action never implies that a Pass was saved, that the window is complete, or that a deficiency was resolved; only the check acknowledgement, obligation state and deficiency lifecycle report those facts.
- **Recorded result on its button (issue #140, owner decision 2026-11-13).** The outcome button matching the current window's recorded result is filled in the result's colour, gains a ✓ and has "(recorded result: …)" added to its accessible name; colour is never the only cue. The result is this person's acknowledged tap until the reloaded row carries that check or a newer one. Otherwise, in a satisfied window, it is the newest check if that check is no older than the satisfaction (`obligation_completed_at`; after a Pass and then a Fail, Fail is marked), and the satisfying outcome if not. A previous window's result, a supervisor completion (even after an Unable check), Not applicable, suspended, exempt or waived rows, and rows with no current window ("No check is currently required", or "Not due" before the window opens; issue #235 B3) mark nothing, even right after this person's tap. The marked button stays an enabled action, and the window tag and "Latest recorded check" line are unchanged.
- **Kit instances.** An item in a kit is listed once per kit instance, labelled by instance, and each save names its `kit_id`. A save on one instance leaves the others pending.
- **Vehicle readings (ODO-1, ODO-3, ODO-4).** The compact form keeps mileage and optional engine hours separate. The first mileage entry selects miles or kilometres; later sessions display and submit the vehicle's established unit, which the server enforces. Each reading keeps its stored unit and historical corrections remain unchanged. Readings are audited history entries, so typing does not save automatically; the explicit Record readings action submits complete values only. An anomalous reading is refused by the server (`ANOMALY_CONFIRMATION_REQUIRED`); the screen then offers "the reading is correct", which is a new decision with a new operation id and `confirm_anomaly`. Changing the value starts a new operation. An unanswered request (including the confirmation) is kept whole, with its operation id, `confirm_anomaly` and explanation, until the server gives a definite answer; the form's submit and the confirmation button both resend it unchanged. Only one reading request is out at a time: its inputs and buttons are disabled until the server answers, so a late answer can never clear or replace a newer unanswered request. An ended session has no readings form, and the script skips the readings wiring so the checklist and socket still start.
- **Reopen.** An ended session shows a Reopen button instead of the controls, with the time until which it can be reopened. Reopening reloads the screen; completed checks keep their original times (SES-4). The other recorded participants are notified that someone reopened it ([notifications](notifications.md#which-events-notify-and-whom), issue #14).
- **Resume deadline (SES-8, SES-9; [issue #256](https://github.com/JustApu/CheckYourAmbulance/issues/256) Part E).** An open session says "This inspection ends by" its deadline. From the deadline the page is read-only for everyone: it says the inspection reached its time limit and that its records are kept, links to the vehicle page to start a new inspection, and shows no Reopen button, readings form or record controls. A check refused with `SESSION_DEADLINE_PASSED` (the deadline passed while the page was open) says so and reloads the screen into that state. The vehicle page offers Resume only before the deadline, with "can be resumed until".
- **Escaping.** Every server value is written with `textContent`, never as markup. The page config is emitted with `json_script`.

## Assumptions and boundaries

1. **Fail and Unable are implemented by [issue #86](https://github.com/JustApu/CheckYourAmbulance-archive/issues/86).** A mismatching count or an explicit Fail/Unable opens the [deficiency workflow](deficiency-workflows.md). The reporter selects an existing report or creates one with category, severity criteria, summary and description; Unable also requires a reason. The full request is retained for retry and conflict acknowledgement. History pages provide own corrections, administrator invalidation and supervisor completion over the existing audited commands.
2. **An odometer entry is not linked to the session.** `POST /api/v1/odometer-entries` still refuses `session_id` (`NOT_YET_SUPPORTED`), so the screen does not send it and an odometer save does not count as session activity (SPEC SES-2) until that is supported.
3. **Session changes are not pushed.** The session commands do not publish `session.changed`, so another viewer sees a join or an end on their next reload, not live. Check, deficiency and odometer changes are pushed.
4. **One checklist version per session.** A session is pinned to the version it opened with. The screen lists only rows of that version; if the vehicle's checklist changed afterwards it says so and asks for a new session.
5. **The basis is the newest effective check for the item and kit instance.** The server compares within the obligation's window, so the screen can show a conflict the server then does not raise, never the reverse.
6. **Saved goes with the row.** With Needs attention only on, a row leaves the list once its check satisfies the obligation, and its Saved indicator leaves with it. The acknowledgement was shown first, and the check stays in history; keeping the row visible until the next reload is a later refinement.
7. **No new front-end tooling.** Like the shell, the stylesheet and script are inline in the page (no static-file serving or build step, SPEC §17); a Content-Security-Policy would need a nonce or served files.

## Verification

It checks the initial overview, accurate mixed-status progress, distinct same-template kit instances, attention-filter exclusion of suspended checks, flat view, target size, no horizontal overflow, refresh restoration for the same user/session, and isolation for another user or new session. Issue #104 adds outcome/window/deficiency combinations, neutral actions and keyboard-accessible action names at those widths. The shell, landing, resume, readings and checklist smoke scripts can save synthetic screenshots when `CYA_BROWSER_EVIDENCE_DIR` points to a private absolute directory. These synthetic browser checks do not replace real-device or screen-reader validation, and do not prove cross-device navigation-state synchronization.

- `cya/inspections/tests/test_crew_ui.py` covers the session endpoints (open, join, replay, SES-7 refusals of a separate start and a second reopen, malformed and non-v4 input, authentication, CSRF, method, participant-only reopen and end, refusals writing nothing), the pages (sign-in redirect, 403 without a role, 404 for unknown, inactive, malformed and other-organization ids, escaping, participant-only session page, config contents, saved preference), and the checklist fields the script records with (version id, newest check and author, and the conflict warning for a stale basis).

It fails on the previous script.
