# Check Your Ambulance

**Status: specification approved / early implementation.** This repository is the starting point for a mobile-friendly EMS ambulance inspection, equipment-readiness and accountability application. Inspection workflows and production deployment remain future work. A Django project provides Google Workspace identity, server authorization and durable audit foundations, with build, lint, migration and offline tests in CI alongside Markdown links, secret scanning and scenario validation. Draft PRs skip CI; the `checks` workflow listens to `synchronize` only to fail fast if an update is pushed while the PR is ready. At handoff, PRs with any non-Markdown path run applicable checks; Markdown-only PRs skip remote workflows and use the local documentation verification gate in [review procedures](docs/review.md#documentation-only-handoff-verification). The Django/MariaDB suite runs for relevant code changes; changes to `docs/data-model-contracts.md` receive its targeted contract test locally. See [Development](#development).

The initial deployment is for one EMS organization, with organization-specific fleet and schedule configuration. The intended system lets multiple crew members independently inspect individual ambulance equipment items, with automatic saving and live shared status. It also tracks equipment/kit inspections, known deficiencies and follow-up verification, station supplies, maintenance, regulatory compliance, and auditable history. An inspection requirement is satisfied by a **valid individual item check**, not by an entire crew rechecking a vehicle.

## Planned capabilities (not yet implemented)

- Vehicle, kit, compartment and equipment checklists with versioned templates and per-item schedules.
- Independent crew member checks, live synchronization, auto-save, concurrency warnings and immutable attribution. Bulk Pass is deferred from R1 and a minimum sealed-kit verification workflow is part of R1 (SPEC 1.2.0, §10.1).
- Known-deficiency visibility, assignment, deadlines, correction, verification and audit trails.
- Operational status and fleet dashboards; supply stock, purchasing, asset maintenance, service contracts and regulatory records.
- Optional scheduled reports and an hourly Humanity schedule feed (API details pending).

## Next steps

The roadmap is tracked in GitHub as `milestone`-labeled tracking issues (M0 onward) with child issues that state their dependencies and what can run in parallel; see [roadmap, milestones and dependencies](docs/coordination.md#roadmap-milestones-and-dependencies).

1. Obtain the initial equipment/checklist definitions and Humanity connection details (see the open items in [SPEC.md §24](SPEC.md#24-decision-register)).
2. Run the architecture spike in [SPEC.md Appendix A](SPEC.md#appendix-a-stack-comparison-note-non-binding) and have the owner approve the stack (OQ-24).
3. Settle the remaining before-production questions in the decision register as the affected features approach release.
4. Create narrowly scoped GitHub implementation issues, following [AGENTS.md](AGENTS.md) and the [coordination rules](docs/coordination.md).
5. Prototype the inspection experience using **synthetic** data, then implement in reviewable increments.

**Stack:** Python with Django and MariaDB 10.11 on Linux, decided by the owner on 2026-10-20 ([SPEC §17.5](SPEC.md#175-hosting-database-engine-backup-oq-24); evidence in [the architecture spike report](docs/spikes/oq24-architecture-spike.md)). Hosting, secrets and recovery are decided in [SPEC §17.8](SPEC.md#178-deployment-secrets-and-recovery-oq-24-issue-16) (one organization-operated Linux VPS, RPO 15 minutes and RTO 24 hours, an off-host encrypted backup held by an authorized operator, and a paper outage fallback). **Still pending:** the provider choice, production setup and the pilot gates in DEP-12, verification of the spike's remaining gaps, actual checklists and external API credentials.

[issue #123](https://github.com/JustApu/CheckYourAmbulance-archive/issues/123) adds [severity re-grading](docs/deficiencies.md#re-grading-severity): a supervisor or administrator (`regrade_deficiency_severity`) changes an active deficiency's severity level through `POST /api/v1/deficiencies/{id}/severity-changes` as an append-only `SEVERITY_CHANGED` event that keeps the previous and new level revision, a mandatory explanation, the actor and the instant, refused if the caller's expected event is stale, and `GET /api/v1/deficiencies/{id}/severity` returns the current level and the grade history. It changes nothing else about the deficiency and never the vehicle's status.
[issue #146](https://github.com/JustApu/CheckYourAmbulance-archive/issues/146) adds [assignment, deadlines and starting work](docs/deficiencies.md#assignment-deadlines-and-starting-work): `POST /api/v1/deficiencies/{id}/assignments`, `/deadlines` and `/work-starts` append `ASSIGNED`, `DEADLINE_SET` and `WORK_STARTED` events (every earlier assignee and deadline retained, Open to In Progress through the SPEC §8.2 table) for Supervisors, Administrators and, on supply-related deficiencies, Supply Officers, never Crew. The assignee must be an active Crew, Supervisor or Supply Officer; `GET /api/v1/deficiencies/{id}/assignment` replays the assignee, deadline and status, now or as of an instant. Notifications are [issue #14](https://github.com/JustApu/CheckYourAmbulance/issues/14).
[issue #149](https://github.com/JustApu/CheckYourAmbulance-archive/issues/149) adds [Awaiting External Dependency and progress notes](docs/deficiencies.md#awaiting-external-dependency-and-progress-notes): `POST /api/v1/deficiencies/{id}/dependencies`, `/dependency-revisions` and `/dependency-exits` (Crew, Supervisors, Administrators and, on supply-related deficiencies, Supply Officers) enter, revise and leave the status with a mandatory explanation, an optional follow-up date that never triggers a reminder, and a return to Open or In Progress as named (by default the status before waiting); `POST /api/v1/deficiencies/{id}/progress-notes` appends an attributed, timestamped note under the same roles (SPEC amendment 1.17.0). `GET .../dependency` and `GET .../progress-notes` read the record, the notes and their history, now or as of an instant.

[issue #150](https://github.com/JustApu/CheckYourAmbulance-archive/issues/150) adds [deadline extensions, overdue state and age](docs/deficiencies.md#deadline-extensions-overdue-and-age): `POST /api/v1/deficiencies/{id}/extension-requests` (Crew, Supervisors and Administrators; a Supply Officer only on a deficiency assigned to them) and `.../extension-decisions` (Supervisors and Administrators approve, deny or choose a different date, with an explanation); each is an appended event and extensions are unlimited. `GET .../deadline` returns the governing deadline (the newest deadline-bearing event, so a new deadline supersedes older approvals), overdue state, age since the report and the extension count, now or as of an instant. An administrator records the age-highlight rule with `POST /api/v1/deficiency-age-rule`; until then nothing is highlighted, and no age-based notification exists (SPEC DEF-5, DEF-6).

[issue #148](https://github.com/JustApu/CheckYourAmbulance-archive/issues/148) adds [operational-status endpoints and screens](docs/vehicle-status.md#http-endpoints-and-screens): `POST /api/v1/vehicles/{id}/status-changes` (Supervisors and Administrators set a status with an explanation, and free-text restrictions for Limited Service), `/status-requests` (Crew and above ask for a change) and `POST /api/v1/status-requests/{id}/decisions` (Supervisors and Administrators approve or deny; a denial needs an explanation), each idempotent on `operation_id`, plus `GET /api/v1/vehicles/{id}/status` (current status, history, pending requests) and `GET /api/v1/status-requests`. The Vehicle status section (`/status/`) shows a vehicle's status and history, the crew request form, the supervisor set-status form and request queue, with honest pending, saved, failed and unconfirmed states and live refresh from the new `status.changed` and `status.request` hints. Status still never changes from any other event. Notifications are [issue #14](https://github.com/JustApu/CheckYourAmbulance/issues/14).
[issue #147](https://github.com/JustApu/CheckYourAmbulance-archive/issues/147) adds the [notification outbox, in-app inbox and email delivery](docs/notifications.md): commands write notification intent in their own transaction (`enqueue`), recipients by role or user are de-duplicated, Administrators set which event/channel pairs are mandatory and users switch the optional ones, and a bounded job sends email through an injected sender with retried, idempotent attempt records (at-least-once, no exactly-once claim). `GET /api/v1/notifications` (your own inbox), `POST /api/v1/notifications/{id}/reads`, `GET`/`POST /api/v1/notification-preferences`, and for Administrators `GET`/`POST /api/v1/notification-policy` and `GET /api/v1/notification-failures`; writes are idempotent on `operation_id`. No event sends a notification yet ([issue #14](https://github.com/JustApu/CheckYourAmbulance/issues/14)), and there is no inbox screen yet.

[issue #79](https://github.com/JustApu/CheckYourAmbulance-archive/issues/79) adds [odometer entries and reading decisions](docs/odometer.md): append-only odometer and engine-hours entries, author corrections and administrator invalidations. `POST /api/v1/odometer-entries` is idempotent on the operation id. Verified commands (Python 3.12+, Docker for the development MariaDB 10.11; prerequisites and details in [CONTRIBUTING.md](CONTRIBUTING.md#python-and-django)):

```sh
python3 -m venv local/venv && local/venv/bin/pip install --require-hashes -r requirements/dev.txt
docker compose up -d --wait db
export CYA_SECRET_KEY=dev-only-not-a-secret CYA_DB_USER=cya_owner CYA_DB_PASSWORD=dev-only-owner-password CYA_DATABASE_ROLE=schema_owner
local/venv/bin/ruff check . && local/venv/bin/ruff format --check .
local/venv/bin/python manage.py check --fail-level WARNING
local/venv/bin/python manage.py makemigrations --check --dry-run
local/venv/bin/python manage.py migrate --noinput
local/venv/bin/python manage.py test cya --noinput
```

Live-update deployments must serve the HTTP publisher and WebSocket consumer
from the same ASGI process. `CYA_ALLOWED_HOSTS` lists explicit host names and
does not accept `*`; see [live-update deployment details](docs/live-updates.md).

[issue #158](https://github.com/JustApu/CheckYourAmbulance-archive/issues/158) adds [explicit ad hoc inspection orders](docs/vehicle-status.md#require-an-ad-hoc-inspection-after-return-to-service-issue-158): Supervisors and Administrators select item/physical-kit pairs, explanation and future due time from the status panel. ## Security and privacy

Do not commit real crew member personal data, operational logs, credentials, API responses, medical/patient data, or production configuration. Use synthetic fixtures and follow the repository's [data hygiene rules](AGENTS.md#github-data-hygiene). Report vulnerabilities privately as described in [SECURITY.md](SECURITY.md).
